# 問題の学び方分類「条件」と「例外」の分割整理

状態: 方針確定・実装前
対象: `questionLearningPatternId`の共通分類

## 目的

現在の「条件と例外を押さえる」は、成立条件を理解する問題と、原則から外れる特別な扱いを理解する問題を一つにまとめています。しかし、学習者が「通常の適用条件を覚えている」状態と、「原則に加えて例外まで理解している」状態では、理解の深さが異なります。

この差を解説の書き方と学習分析へ反映できるよう、次の二分類へ分けます。

| ID案 | 表示名 | 判断する内容 | 解説の基本構成 |
| --- | --- | --- | --- |
| `conditions_scope` | 条件と範囲を押さえる | いつ、誰に、何に、どの数値・期間・範囲で規定や知識が成立するか | 正誤 → 成立する条件・範囲 → 境界の内外 |
| `principles_exceptions` | 原則と例外を押さえる | 通常のルールと、それが適用されない場合又は別の扱いになる場合 | 正誤 → 原則 → 例外となる条件 → 例外時の扱い |

## 分類の境界

### 条件と範囲を押さえる

次のように、通常の規定や知識が成立する条件を判断する問題を割り当てます。

- 「Aの場合はBとなる」
- 「X以上・未満なら対象となる」
- 「基準日前Yか月以内なら認められる」
- 対象者、設備、期間、地域、数値又は適用範囲を確かめる

条件を満たすかどうかで結論が決まり、原則から外れる特別な扱いを理解する必要がなければ、この分類です。

### 原則と例外を押さえる

次のように、通常のルールを理解したうえで、その適用を外す又は変更する特別な扱いを判断する問題を割り当てます。

- 「原則はAである。ただし、Bの場合はCとなる」
- 「Aを必要とする。ただし、Bを除く」
- 「Bの場合は、この限りでない」
- 免除、除外、特例、経過措置又は代替手段を確かめる

`ただし`、`除く`、`この限りでない`という語だけでは決めません。通常のルールから結論が外れる構造になっていることを確認します。

## 迷う場合の決め方

一肢を一つの分類へ割り当て、正答を導くために最後に必要となる理解を主分類にします。

1. 数値、期間、対象又は範囲へ当てはめて結論を出すなら「条件と範囲を押さえる」。
2. 原則を確認した後、その問題だけ原則を外す必要があるなら「原則と例外を押さえる」。
3. 例外が数値条件で発動する場合でも、問われている中心が原則からの離脱なら「原則と例外を押さえる」。
4. 元の設問が複数の記述をまとめていても、整備後の独立した一肢ごとに分類する。

先に確認したガス主任技術者試験の「基準日前4か月以内に漏えい検査を行った場合は、基準日に検査したものとみなす」は、検査日として認められる期間を問うため「条件と範囲を押さえる」に分類します。

## 学習者へのフィードバック

分類を分けることで、同じ法令・制度問題の誤答でも、次のように原因を区別できます。

- 「条件と範囲を押さえる」が弱い: 数値、期間、対象者又は適用範囲の確認が不足している。
- 「原則と例外を押さえる」が弱い: 原則は理解しているが、除外、特例又は例外時の扱いまで整理できていない。

前者には条件を表で整理する学習、後者には「原則 → 例外 → 例外時の結論」を対にして復習する学習を提案できます。

## 実装時の扱い

この文書の段階では、現行の分類カタログ、問題整備プロンプト、アプリ、保存済みデータ及びFirestoreを変更しません。実装時は次を一つの変更として整合させます。

1. `config/question_learning_patterns.json`を八分類へ更新する。
2. `prompt/03_prompt_add_explanationText.md`の分類表、例、完成確認を更新する。
3. 検証コード、テスト及びアプリ側カタログを同じIDへ更新する。
4. 既存の`conditions_exceptions`は一律に新IDへ置換せず、各肢を「条件」と「例外」のどちらかへ再分類する。
5. 旧IDを新しい意味へ流用せず、移行完了後に残さない。

実際の過去問による「原則と例外を押さえる」の代表例と迷いやすい例は、文章と分類の認識を合わせた後、03の例へ反映します。
